## §2.1 热输运理论

**篇幅**：约 1500 字  
**写作总思路**：先分述三种基本热传递机制（各有独立小节），再集中讨论多机制耦合问题，最后以"现有数值方法难以高效耦合求解"作为动机，自然引出蒙特卡洛路径追踪统一框架。三种机制的篇幅按建模深度分配：**传导 > 辐射 > 对流**（对流建模最少，一段带过）。

### §2.1.1 热传导

- 物理机制：声子碰撞（非金属）/ 自由电子迁移（金属），宏观服从局域热平衡假设
- **傅里叶定律**：$\mathbf{q} = -\lambda \nabla T$，说明各符号含义及各向同性假设
- **热传导方程**：由能量守恒推导 $\rho c_p \frac{\partial T}{\partial t} = \nabla \cdot (\lambda \nabla T) + \dot{S}$，指出体积热源项 $\dot{S}$ 的耦合角色
- 三类边界条件：Dirichlet（给定温度）、Neumann（给定热流）、Robin（混合）
- **【重点强调】热传导在耦合求解中的主导地位**（三个层面）：
  1. 三维抛物型 PDE，求解域为固体体积，维度远高于表面辐射
  2. 蒙卡随机游走代价高：大量短步长采样 + 每步一次几何相交查询，样本数远超辐射路径
  3. 耦合迭代收敛受制于传导弛豫时间，而非辐射/对流边界交换速率
  → 引出 GPU 硬件光追加速的核心动机

**公式**：傅里叶定律、热传导方程（含时间项与稳态简化形式）  
**引用**：`\cite{bergmanFundamentalsHeatMass2011}`

---

### §2.1.2 热辐射

- 物理机制：电磁波传能，无需介质，是红外仿真的重要机制
- 黑体辐射：普朗克分布、**Stefan-Boltzmann 定律** $E_b = \sigma T^4$
- **Kirchhoff 定律**：热平衡下 $\varepsilon_\lambda = \alpha_\lambda$，为材料参数统一描述提供依据
- **辐射传输方程（RTE）**：$\hat{\omega} \cdot \nabla L = \kappa(L_b - L) - \sigma_s L + \frac{\sigma_s}{4\pi}\int_{4\pi} L \, d\hat{\omega}'$，三项分别对应热发射增益、出散射衰减、入散射补偿
- 本文简化：漫射灰体假设 + 不透明固体间辐射，介质透明时 RTE 退化为直线传播 → 光线追踪成为天然工具

**公式**：Stefan-Boltzmann 定律、Kirchhoff 定律、RTE 微分形式  
**引用**：`\cite{modestRadiativeHeatTransfer2013,howellThermalRadiationHeat2021}`

### §2.1.3 热对流

**（篇幅精简，约 100 字正文）**

- 物理机制：fluid 宏观运动携带热量，固-流界面产生对流换热
- **牛顿冷却定律**：$q_\mathrm{conv} = h(T_s - T_\infty)$，$h$ 是集总流场信息的换热系数
- **本文建模立场**：不求解 N-S 方程；对流仅以边界条件（CNV 过程）形式参与，$h$ 由用户预先指定。这是工程热仿真的标准解耦简化，在本文精度范围内合理。

**公式**：牛顿冷却定律（一行）  
**引用**：`\cite{bergmanFundamentalsHeatMass2011}`

### §2.1.4 多机制耦合热输运

- 工程场景动机：三种机制同时存在（飞行器壁面热防护 / 红外特征预测），不可单独求解
- **边界耦合**（联合能量平衡边界条件）：
  $$-\lambda\nabla T\cdot\hat{n} + h(T_s - T_\infty) + \varepsilon\sigma T_s^4 - \alpha G = 0$$
  $T_s$ 由传导热流、对流热损失、净辐射热流共同决定，$T^4$ 项导致高度非线性
- **体积耦合**：半透明固体中辐射吸收项 $\dot{S} = \kappa\int_{4\pi} L\,d\hat{\omega} - 4\kappa\sigma T^4$ 直接作为热传导体热源
- 数值挑战：$T^4$ 非线性、时间尺度跨越多个数量级、各机制离散格式不统一
- **引出蒙卡路径追踪**：统一路径空间中三种机制自然描述，避免跨模块耦合迭代
- **GPU 加速动机伏笔**：统一路径空间后所有过程（RAD/BND/CND/CNV）大量依赖同构几何射线查询 → 天然适合批量并行 → RT Core 加速

**公式**：联合边界条件方程、体积耦合能量方程  
**引用**：`\cite{batiCouplingConductionConvection2023,howellThermalRadiationHeat2021}`

## §2.2 蒙特卡洛热输运求解方法

**篇幅**：约 2500 字（全章核心节）  
**写作总思路**：基础原理（§2.2.1）→ 早期热辐射应用（§2.2.2）→ 路径追踪现代表述（§2.2.3）→ Bati 等人统一框架（§2.2.4，重点）→ 原始逐路径递归求解器实现（§2.2.5，直接为第三章铺垫）

### §2.2.1 蒙特卡洛积分方法

- 核心思想：随机样本经验均值估计积分，估计量 $\hat{I}_N = \frac{1}{N}\sum_{i=1}^N \frac{f(x_i)}{p(x_i)}$，方差 $O(N^{-1/2})$ 收敛
- 重要性采样：$p(x)\propto|f(x)|$ 最小化方差；多维积分中与确定性方法相比无维数灾难
- 物理可解释性：每条路径是一个样本，贡献权重即 $f(x)/p(x)$

**公式**：MC 估计量、方差公式、重要性采样估计量  
**引用**：`\cite{howellMonteCarloSolution1964}`（历史溯源）

### §2.2.2 热辐射的蒙特卡洛求解

- 经典正向追踪：发射能量包 → 追踪吸收/反射 → 统计各表面能量沉积
- Howell (1964) 奠基性工作：首次系统将 MC 应用于辐射传热计算
- 局限性：正向追踪对复杂场景收敛慢 → 引出反向路径追踪动机

**公式**：辐射交换因子的 MC 估计

### §2.2.3 路径追踪方法

- **渲染方程**（Kajiya 1986）：$L_o = L_e + \int_\Omega f_r L_i (\hat{\omega}_i\cdot\hat{n})\,d\hat{\omega}_i$，递归积分方程
- 路径积分表述：展开递归为路径空间高维积分，MC 采样 = 随机生成路径
- 反向路径追踪（eye path tracing）：从探测器出发，只计算对观测有贡献的路径 → 适合红外成像仿真
- **null-collision 技术**：虚拟碰撞均匀化消光系数，消除介质中的条件分支，使步进无偏

**公式**：渲染方程、路径空间测度、null-collision 均匀消光表达

### §2.2.4 单路径空间耦合求解框架

- **Bati et al. 2023 核心贡献**：传导、对流、辐射三种机制统一为"广义路径"，在单一路径空间构造无偏估计量
- 三类路径段：
  - **辐射段（RAD）**：光子直线传播，Fermat 折射
  - **传导段（CND）**：固体内布朗随机游走，Kac 公式关联 Green 函数：$u(x) = E_x[g(B_\tau)]$
  - **对流段（CNV）**：固-流界面能量转移，路径终止或分叉
- **耦合事件（BND）**：固-气界面以概率分叉——以发射率概率进入辐射段，$(1-\varepsilon)$ 概率继续传导，对流换热权重转移给对流段
- 路径权重递推：每次事件乘以 BRDF / 透过率 / 换热权重，累计贡献到探测器像素
- **本文实现简化**：一阶 Picard 迭代（线性化 $T^4$）；传导段以有限元/有限差分数值求解 Fourier 方程

**公式**：耦合路径估计量、Kac 公式

### §2.2.5 原始 CPU 求解器的 DFS 实现

### §2.2.6 DFS 求解框架的局限性分析

**（本节从原第三章 §3.3 移入并精简，为 §2.3 Wavefront 动机提供直接铺垫）**

**篇幅**：约 600 字  
**写作思路**：从 §2.2.5 DFS 实现出发，分析其面向并行化改造时的四大结构性障碍，四者均源于同一根因——路径状态与执行控制流的隐式耦合。

#### 障碍 A：调度粒度过大
- DFS 将完整路径封装为一次连续函数调用链（RAD→BND→CND→CNV 全部逻辑），粒度锁定在完整路径生命周期
- 映射为 MegaKernel 时寄存器需求极高、递归深度受栈空间限制、warp 内分叉严重

#### 障碍 B：路径状态不可持久化
- 路径全部中间状态分散在多层调用栈帧局部变量中，是控制流的副产物而非独立数据对象
- 无法在查询途中以快照形式导出——函数不等待结果无法正常返回，强行返回栈帧释放状态不可恢复

#### 障碍 C：几何查询请求无法批量积累
- 批量化要求同时积累多条路径的查询请求后统一提交
- DFS 同步阻塞结构使第一条路径查询占用控制流直至结果返回，其他路径无法推进
- 即使多线程化各线程仍独立阻塞，提交宽度恒为 1

#### 障碍 D：复合物理分支无法拆分调度
- BND 界面事件产生运行时概率分叉 + null-collision 循环 + 递归子路径树
- 以嵌套函数调用形式展开，不同路径分支选择完全异步，无法统一调度

#### 局限性总结
- 四者层层递推：障碍 B → 障碍 C → 障碍 A + 障碍 D → 批量化不可行
- 解决方向：将路径状态从调用栈显式提取为可序列化数据结构，将状态推进与查询执行解耦——引出 §2.3 Wavefront 执行模型

## §2.3 Wavefront 执行模型

**篇幅**：约 1000 字  

**写作核心定位说明**（不写入正文）：  
本文的 Wavefront 实现是 **CPU 多线程**，无 GPU 实现，且 CPU 端并不按状态对路径进行分桶排序，而是线性遍历路径数组，将每条路径从当前计算状态推进到下一个需要 GPU 计算的 PENDING 状态（按 GPU 任务类型分为 RT / ENC / CP 三类）。  
真正的性能主导问题**不是 Warp 发散**（CPU 无此约束），而是：  
1. **DFS 的同步耦合结构使批量 GPU 查询无法成立**——这才是引入 Wavefront 解耦思想的根本动机；  
2. **状态结构体数组的 Cache 压力**——同时维护 N 条路径状态的内存工作集远超缓存容量，是本实现的头号性能瓶颈，也是相对 DFS 对照组引入的独有代价。  
Warp 发散可在引出原始论文背景时一句带过，不能作为本节主逻辑链。

**写作总思路**（重新设计）：从 DFS 障碍到批量化需求（§2.3.1）→ Wavefront 范式：解耦状态推进与查询执行（§2.3.2）→ 适用性分析与解耦引入的 Cache 代价（§2.3.3）。

---

### §2.3.1 从 DFS 障碍到批量化需求

**（简要衔接 §2.2.6 与 Wavefront 范式，约 3 句话）**

- §2.2.6 的四大障碍分析揭示了 DFS 架构无法实现批量几何查询的根本结构性原因：路径状态与执行控制流的隐式耦合。
- 其中，障碍 B（路径状态不可持久化）和障碍 C（查询请求无法批量积累）指向最直接的解法方向——将状态推进与查询执行从同一控制流中解耦为两个独立阶段。
- 这正是 Wavefront 执行范式的核心思想。

---

### §2.3.2 Wavefront 范式：解耦状态推进与查询执行

- **核心思想**（硬件无关表述）：让每条路径维护一个持久化的状态结构体，CPU 负责驱动路径在状态机中前进；当路径抵达需要几何查询的节点时，不立即执行查询，而是将查询请求写入对应的**挂起队列**（pending queue），路径进入 **PENDING 状态**挂起。CPU 继续推进其他路径，直至一批挂起请求积累完毕，再统一提交给几何查询后端执行，结果返回后路径从 PENDING 状态恢复继续推进。
- **解耦的直接效果**：状态机推进（CPU 密集）与几何查询（可并行/可批量卸载）成为两个独立的执行阶段，前者不再阻塞后者，批量查询自然涌现。
- **起源背景**（一句带过）：Laine et al. 2013 在 GPU 路径追踪中提出这一模式（原始动机是解决 Megakernel 架构下的 Warp 发散和寄存器压力问题），但其解耦结构的价值独立于具体硬件：在 GPU 上，挂起路径对应 kernel 间的全局显存队列；在 CPU 上，挂起路径对应线程池共享的内存数组。
- **本文的 PENDING 分类**：耦合热输运求解涉及三类不同的几何查询，对应三类 PENDING 状态——**RT**（射线最近命中，用于 RAD 辐射路径传播）、**ENC**（封闭腔体归属查询，用于 BND 界面事件）、**CP**（最近面投影，用于 CND 传导段边界判断）；CPU 推进路径直至进入其中一类 PENDING，随后批量提交至 GPU 后端（OptiX 管线），构成第四章三条管线设计的直接来源。

**图表**：Wavefront 双阶段循环示意（CPU 推进阶段：遍历路径数组，将到达查询节点的路径写入 pending queue；GPU 执行阶段：批量处理 RT/ENC/CP 请求，结果写回，路径恢复推进）  
**引用**：`\cite{laineMegakernelsConsideredHarmful2013}`

### §2.3.3 适用性分析与解耦引入的 Cache 代价

- **对耦合热输运的适用性**：四类状态（RAD/BND/CND/CNV）在路径状态机中自然交替，每条路径在某次状态转换后可能需要 RT、ENC 或 CP 任一类查询。CPU 只需按顺序遍历路径数组，将各路径推进至 PENDING，不需要按状态排序分桶（排序会引入额外的数据重排开销，且在路径数量有限时收益不明显）；批量查询的积累是遍历本身产生的自然副产品。
- **解耦引入的新代价：状态结构体数组的 Cache 压力**：  
  - DFS 对照组（stardis-cpu）：同一时刻只维护**一条**路径的状态，状态数据完全在调用栈上，CPU L1/L2 Cache 可完全覆盖，访问延迟极低；  
  - Wavefront 实现：需同时将 $N$ 条路径的状态结构体长期驻留于内存（每个结构体含位置、方向、权重、命中信息、封闭腔体编号等字段），$N$ 较大时工作集远超 Cache 容量，CPU 推进阶段的遍历对每条路径的随机访问几乎均为 Cache miss，产生显著的内存访问延迟；  
  - 这是本实现**头号性能瓶颈**，也是相对对照组引入的独有代价，在对照组中完全不存在。  
  - 此代价与架构本身是内在绑定的——持久化路径状态是实现解耦的必要条件；优化方向（如 SoA 布局、状态结构体精简）将在第三章讨论。
- **小结**：Wavefront 解耦使批量 GPU 几何查询从根本上成为可能，但以 Cache 压力为代价；理解这一权衡是第三章性能分析的基础，也是本文混合架构设计的核心取舍。

**引用**：`\cite{laineMegakernelsConsideredHarmful2013}`

### ⚠️ §2.3.3 重要论述逻辑权衡（已否决方案存档）

**被否决写法**：在论述 Cache 代价时，点出"该代价是 CPU 扫描路径状态对象以实现批量处理的固有代价；若采用 GPU SIMT，路径状态以 SoA 布局存于显存，各 warp 线程并行各取自己的状态分量，不存在 CPU 顺序扫描的工作集溢出问题，该代价不存在"。  
对应的逻辑安排：§2.3.3 结尾以"GPU SIMT 可消除此代价"收束 → 暗示第四章 GPU 选择是对该代价的自然解法。

**否决理由（两条）**：

1. **技术成立性有重要限定**：该说法对"纯 GPU Wavefront"成立（如 PBRT-v4 GPU 模式），但本文实现是 CPU-GPU 混合架构——路径状态仍由 CPU 维护和扫描，GPU 仅承担几何查询执行阶段；因此 CPU Cache 压力在本架构中**不因引入 GPU 查询后端而消失**，说"GPU SIMT 消除该代价"混淆了"全 GPU Wavefront"与"CPU 扫描 + GPU 查询"两种架构。

2. **论述结构问题**：若 §2.3.3 明确指出"GPU SIMT 可消除此代价"，会引入一个论文无法收场的隐含追问——"既然 GPU 消除了 Cache 代价，为何不把路径状态管理也迁移到 GPU？"第四章只回答了"批量查询用 GPU"，从未展开论证"为什么不做全 GPU Wavefront"（该答案涉及耦合求解逻辑的条件分支复杂性、数据依赖等，未在本文范围内）。此外，该写法从另一角度（Cache 而非批量化）使 §2.3.3 重新成为第四章 GPU 选择的铺垫，与上轮"保持第四章独立性"的修订目标相悖，只是换了形式。

**正确立场（当前文本所采用）**：Cache 代价作为 CPU Wavefront 实现的**独有内在权衡**，定性描述其与批量规模 $N$ 的关系（$N$ 越大，批量效果越好，Cache 压力越大），结论落在"这是实现解耦的必要代价"，不引入 GPU 对比。若要提 GPU 内存访问的优势，正确位置是**第四章引言**，在那里作为选择 GPU 后端的动机之一出现——是第四章自己的论据，而非从第二章推出的结论。

## §2.4 光线追踪与几何查询加速技术

**篇幅**：约 2000 字  
**写作总思路**：光线-几何求交基础算法（§2.4.1）→ BVH 加速结构（§2.4.2）→ CPU 实现 Embree（§2.4.3）→ GPU 硬件加速（§2.4.4）→ 本文涉及的三类几何查询（§2.4.5，直接铺垫第四章三条管线）。

### §2.4.1 光线-几何求交算法

- 问题定义：光线 $\mathbf{r}(t) = \mathbf{o} + t\hat{\mathbf{d}}$，求与场景三角形网格的最近交点 $(t^*, u^*, v^*)$（重心坐标）
- **Möller-Trumbore（MT）算法**：Cramer 法则求解，1 次叉积 + 3 次点积，无需预计算法向量 → 概念参考实现，结构简洁但**不满足水密性**
- **为什么需要水密性**：共享棱边处两三角形各自独立浮点计算，掠角情形下舍入误差导致两类失效——穿透缝隙（双重漏判）或双重命中；在蒙特卡洛热输运中，穿透失效使粒子进入错误腔体，腔体归属（`enc_id`）出错导致系统性偏差，无法通过增加样本量消除；低仰角红外成像（掠角观测）对此最为敏感
- **BWB 水密算法（Wald-Benthin-Woop）**：预计算 $3\times4$ 仿射变换矩阵将三角形映射到射线对齐坐标系；在线查询以三个棱函数 $e_0, e_1, e_2$ 的符号一致性判别命中；将 $e_i=0$ 归入正方向侧，保证相邻三角形对共享边界恰好一方声明所有权，彻底消除双重漏判与双重命中
- **BWB 是工业标准**：Embree 默认求交内核（配合 SIMD 批量射线包）；NVIDIA RT Core 固定功能求交电路的硬件设计基础

**公式**：光线参数方程、MT Cramer 解、BWB 棱函数 $e_0, e_1, e_2$  
**引用**：`\cite{MollerTrumbore1997,WaldBenthinWoop2013}`

### §2.4.2 层次包围体加速结构（BVH）

- 暴力检测复杂度 $O(N)$，百万面片场景不可接受
- **BVH 核心思想**：场景三角形组织为 AABB 二叉树，光线先与包围盒测试快速剪枝，平均复杂度降至 $O(\log N)$
- **SAH 构建策略**：$C = c_t + \frac{A_L}{A}N_L c_i + \frac{A_R}{A}N_R c_i$，选代价最小的分割；实践中用 binning 近似控制构建时间
- 遍历：栈式 DFS，子节点按 $t_\text{near}$ 排序，及时利用当前最近距离 $t^*$ 剪枝
- 其他结构简述：KD-Tree（紧凑但构建慢）、Grid（均匀场景有效）

**公式**：SAH 代价函数  
**图表**：BVH 树结构示意图（包围盒层次 + 对应二叉树节点）  
**引用**：`\cite{ailaUnderstandingEfficiencyRay2009}`

### §2.4.3 CPU 光追加速：Intel Embree

- 定位：Intel 高性能 CPU 光追内核库，是本文 CPU Baseline（stardis-cpu）的几何相交后端
- 关键技术：
  - SIMD 并行（SSE4/AVX2/AVX-512）：射线包（ray packet）遍历，宽度 4/8/16 条
  - 多叉 BVH（MBVH）：4 叉（QBVH）/ 8 叉（OBHV），与 SIMD 寄存器宽度对齐
  - 针对不同几何类型的专用求交内核（三角形、曲线、细分曲面）
- API 分级：`rtcIntersect1()`（单条）/ `rtcIntersect4/8/16()`（packet 模式）
- **本文基准求解器实际仅使用 `rtcIntersect1()`**：DFS 架构下同一时刻仅有单条路径的查询请求就绪，packet 所需的批量同构射线无法被 DFS 结构自然积累——这正是 §2.3.1 批量化障碍在 Embree 接口层的直接体现，受限于上层架构设计而非 Embree 能力
- 典型性能：单条射线 ~$10^7$ rays/s；packet 模式可进一步提升 4--8 倍（基准求解器受架构限制仅获得前者）
- 本文角色：Baseline 几何后端，与第四章 GPU 批量查询后端性能对比

**引用**：`\cite{waldEmbreeKernelFramework2014,EmbreeRayTracing}`

---

### §2.4.4 GPU 硬件光追加速

- **RT Core**（NVIDIA Turing 起，Ampere 为第二代）：专用固定功能单元，与 CUDA Core / Tensor Core 独立，负责 BVH 遍历 + 光线-三角形求交
- 执行流程：`optixTrace()` → RT Core（BVH 遍历 + 求交，对 CUDA 透明）→ 命中触发 Closest-Hit / Any-Hit / Miss Shader（在 SM 上执行）
- 性能：RT Core 与 SM 并行工作，高并发查询下吞吐量可达 Embree（单核）的 5～10 倍
- **OptiX 编程模型**：封装 RT Core，提供 Pipeline / SBT（Shader Binding Table）机制，支持用户自定义 Intersection / Closest-Hit / Any-Hit / Miss 程序

**图表**：GPU SM 与 RT Core 协同流水线示意图（`optixTrace` → RT Core → Shader）  
**引用**：`\cite{parkerOptiXGeneralPurpose2010}`

### §2.4.5 本文涉及的几何查询类型

**（本节定位：引出三类查询的物理语义与驱动目的，具体实现管线设计留给第四章。）**

| 查询类型 | 缩写 | 驱动过程 | 正文描述实现方式 |
|---------|------|---------|----------------|
| 最近命中光追 | RT | RAD/BND/CND 各涉及直接射线求交的过程 | OptiX Closest-Hit 管线（最直接支持，批量规模最大） |
| 最近面投影 | CP | CND 游走步长计算（**仅 WoS 传导变体**，当前 delta-sphere 不用） | 场景表面最近点批量查询（实现细节第四章展开） |
| 封闭腔体归属查询 | ENC | BND 腔体归属判断 | 多方向探测射线 + 法向判侧（实现细节第四章展开） |

**各查询关键事实（正文所述，供第四章设计参考）**：

- **RT**：并非仅 RAD 产生——RAD 传播步、各类 BND 界面步骤（反射/对流启动/外部重注入）、CND WoS fallback 均会提交 RT 查询，是三类中批量规模最大的。
- **CP**：仅 WoS 传导路径需要（以最近距离确定球半径，粒子进入 epsilon-shell 时触发 BND）。**当前部署 delta-sphere 变体，CP 队列恒为空**（delta-sphere 用一对相对方向短程射线对估计步长，不依赖 CP）。
- **ENC**：向场景发射多条探测射线，以命中面法向与射线方向点积的符号判定内/外侧，再查腔体编号表。具体射线取向策略与 fallback 逻辑见第四章。

**实现背景（仅供 outline 参考，不出现在正文）**：  
- ENC：6 轴对齐基础方向经 R(π/4,π/4,π/4) 旋转；有效性过滤：距离 > 1e-6、|cos(N,d)| > 1e-2；首层全败 → 对角 fallback (1,1,1)/√3；再败 → 同步调用 `scene_get_enclosure_id()` 保底。（源码：`sdis_wf_steps_enc.c`）  
- CP：`s3d_scene_view_closest_point()` 批量接口，底层实现见 oxstar-3d；`sdis_wf_steps_cnd.c` 中 WoS 分支。

**引用**：`\cite{parkerOptiXGeneralPurpose2010}`
