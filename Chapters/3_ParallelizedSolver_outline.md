## §3.1 引言

**篇幅**：约 500 字  
**写作思路**：

1. **衔接第二章**：回顾耦合热输运蒙特卡洛方法的计算特点——路径内多次异构几何查询（RT/ENC/CP）、递归物理分支（RAD→BND→CND→CNV）、高 SPP 要求（像素级采样）导致总查询量巨大。
2. **核心矛盾**：DFS 的同步阻塞调用结构使路径执行与几何查询紧密耦合——每次 `trace_ray` 必须等待结果返回才能推进路径状态，不同路径之间无法积累批量请求。海量路径的几何查询只能逐条分散发出，批量化在架构层面根本无从成立，几何查询后端的吞吐量潜力因此无从利用。
3. **本章目标**：在保持物理等价的前提下，将 递归求解器等价改造为 Wavefront 批处理架构——通过显式化路径状态、解耦状态推进与查询执行，使批量几何查询成为可能，并构建相应的 CPU-GPU 混合执行框架；同时从物理一致性和性能两个维度对改造结果进行实验验证。
4. **章节组织**：§3.2 从算法层面推导 Wavefront 设计约束（挂起点分析 → 状态字段 → 三类查询规约）；§3.3 提出状态机等价变换、Wavefront 执行模型和混合架构；§3.4 报告实验结果；§3.5 总结并引出第四章。

### (2) 实例分析一：RAD 辐射传播段的 RT 查询挂起点

以 `find_next_fragment`（`sdis_heat_path_radiative_Xd.h`）为例，展示 RT 查询如何嵌入 DFS 调用链：

```
trace_radiative_path(scn, dir, ctx, rwalk, rng, T)
  → find_next_fragment(scn, rt_pos, in_dir, in_hit, time, enc_id, ...)
    [*] trace_ray(scn, rt_pos, in_dir, ∞, enc_id, in_hit, &hit)   ← 同步阻塞
        scene_get_interface(scn, hit.prim.prim_id)
        setup_fragment(&frag, pos, in_dir, time, N, &hit)           ← 使用 hit
```

**[*] 处挂起时须持久化**（"查询返回后仍需使用的当前帧及祖先帧局部变量"）：
- `rt_pos`：射线起点（查询参数；恢复后仍需计算命中位置）
- `in_dir`：传播方向（查询参数；恢复后 `setup_fragment` 仍需）
- `enc_id`：当前腔体（查询过滤参数；同时决定界面物理参数查找）
- `in_hit`：前序命中记录（自相交过滤，防止再次命中出发面）
- `time`：仿真时刻（`setup_fragment` 在恢复后调用时需要）
- `phase`：相位标识（标记"挂起在 RAD 弹射 RT 查询处"，恢复时分发依据）

### (3) 实例分析二：WoS 传导段（CND）的 CP + RT 双重挂起点

以 `sample_next_position`（`sdis_heat_path_conductive_wos_Xd.h`）为例，展示同一函数内两类不同性质挂起点：

```
sample_next_position(scn, rwalk, rng, delta, &distance)
  [A] scene_view_closest_point(view, wos_pos, ∞, NULL, &hit)      ← CP 查询
      wos_distance = hit.distance
      if wos_distance ≤ ε_shell(delta): setup_hit_wos(...)
      else: dir ← sphere_uniform(rng); pos = rwalk->vtx.P + dir * wos_distance
          check_diffusion_position(scn, rwalk->enc_id, delta, pos)
          if invalid:
            [B] scene_view_trace_ray(view, rt_pos, rt_dir, ..., &hit_rt)  ← RT 回退
```

- **[A] CP 查询**挂起时须持久化：`rwalk->vtx.P`（游走位置，查询原点）、`rwalk->enc_id`（腔体，界面侧判断）、`delta`（步长参数，决定 ε-shell 阈值）、`rng` 状态（恢复后方向采样需继续此随机序列）。
- **[B] RT 回退查询**（仅在 [A] 恢复后位置合法性验证失败时发生）：共享 [A] 大部分字段，须额外保存 [A] 恢复后已采样的 `dir` 和候选位置 `pos`。两个调用点虽同处一函数，查询类型不同，须分配独立的相位标识。

---

### (4) 通用规律

> **DFS 调用栈中每一个几何查询调用点，其挂起时所需持久化的状态集合，精确等于该调用点所在帧及全部祖先帧中"查询返回后仍需使用的局部变量"之并集。**

将此方法扩展到 `stardis-cpu` 递归求解器（`sdis_heat_path_*.h` 系列）中全部 `scene_view_trace_ray` 和 `scene_view_closest_point` 调用点，即可完整枚举所有挂起点及其持久化需求。

---

### (5) 全算法挂起点汇总表（19 个调用点，三类查询）

表格列：**调用点所在物理过程 | 查询类型（RT/ENC/CP）| DFS 源文件定位 | 查询描述 | §3.3 对应 `path_phase` 状态（对照）**

三类查询的物理必要性：
- **RT 查询（14 个）**：路径追踪基本操作，覆盖辐射弹射、各类界面重注入、传导步长估计、对流初始化、外部净通量子流程，无法回避。
- **ENC 查询（3 个）**：耦合热输运特有。多腔体场景中每个封闭腔体有独立的 ε、λ、h，BND 事件须先确定所属腔体才能查找正确参数。纯辐射渲染不涉及此查询。
- **CP 查询（2 个）**：WoS 传导游走特有。步长上界等于游走点至最近面的投影距离，比等价的 delta-sphere（随机双向射线对）方案对稠密固体内部更为高效；两方案在实现中并存以适应不同几何环境。

三类查询的划分依据是**物理计算需求**。在本文的 Wavefront 实现（`stardis-oxs3d-merge-phase`）中，ENC 查询与 CP 查询均已实现后端化（第四章详述），与 RT 查询共享同一批量查询接口——由此，全部 19 个挂起点成为**同构挂起点**：Wavefront 主循环无需区分查询类型，统一收集、统一提交、统一恢复，调度逻辑大幅简化。

---

### (6) 路径状态最小必要字段集（文字归纳，不设独立表格）

对 19 个调用点逐一应用上述分析方法后取并集，归纳为五类字段（文字描述，不作独立表格——字段的具体定义与冷热分层布局在 §3.3 中展开）：
1. **几何与传播状态**：位置、方向、腔体编号、前序命中记录（RT/ENC/CP 全部调用点）
2. **物理路径参数**：仿真时刻、Picard 分支计数、温度估计量（BND 与终止判断调用点）
3. **随机数状态**：per-path CBRNG 密钥 + 计数器（所有调用点，确定性恢复）
4. **过程局部变量联合体**：WoS 步长参数、BND 各分支临时量、PicardN 子路径递归栈等（对应物理过程调用点）
5. **相位标识**：标记当前挂起在哪个调用点，状态机恢复分发依据

字段集合与 DFS 执行到该调用点时整个调用栈局部变量信息量**完全等价**——每个字段均能追溯到至少一个调用点的恢复需求，无冗余字段，无遗漏字段。

---

### (7) 小结

以 `stardis-cpu` DFS 实现为出发点，通过 RAD 弹射和 WoS 传导两个具体实例建立分析方法，推广到全算法 19 个几何查询调用点，识别出三类查询（RT/ENC/CP）和五类字段。这些约束**完全由算法的物理计算需求决定**，是 §3.3 节状态机设计的直接依据。§3.3 的 `path_phase` 枚举（59 个状态值）与此 19 个调用点一一对应（每调用点对应一对挂起/恢复状态），是规约与实现无缝衔接的验证。

## §3.3 Wavefront 耦合热输运求解器实现（原 §3.4）

### §3.3 节首（~300字，不单独成节）

**写作思路**：进入子节之前，用 1–2 段文字明确 Wavefront 架构思想与两个结构性前提：

1. **定义 Wavefront**：将原 DFS "对每条路径递归到底"的求解模式，重构为以**路径池**为单位的迭代循环——`推进 → 收集查询 → 批量执行 → 回填结果`，每次迭代全部活跃路径同步推进一步。

2. **两个结构前提（§2.2.6 四大障碍的直接解法）**：
   - **前提 A（可挂起性）**：路径在任意查询调用点被暂停时，其完整状态可持久化到外部结构体，查询返回后可无损恢复。（对应 §2.2.6 障碍 B：状态无法持久化）
   - **前提 B（可聚合性）**：暂停中的多条路径的查询请求可以聚合为批次统一提交，推进逻辑与查询执行在时序上解耦。（对应 §2.2.6 障碍 C：查询无法批量化）

3. **宣告结构**：§3.3.1 设计满足前提 A 的显式状态机；§3.3.2 利用前提 A 建立满足前提 B 的执行模型；§3.3.3 利用批量接口实现两角色异构并发调度。

#### (2) 辐射传播模块（RAD）——渲染方程驱动的多次弹射（约 500 字）

**物理背景**：

- 对应 Bati Eq. 6（简化渲染方程，灰体漫射表面）与 Eq. 19（辐亮度温度 $\theta_R = E[\theta_S(\mathbf{x}_\Gamma)]$）。
- 物理含义：从红外相机出发的路径在透明流体中沿直线传播，遇到不透明固体表面时以概率 $\varepsilon$ 被吸收（路径终止于此表面，权重为 $\theta_S(\mathbf{x})$），以概率 $1-\varepsilon$ 发生漫反射或镜面反射后继续传播。
- 这是耦合路径的"外层循环"：路径从相机出发，经过若干次辐射弹射到达某个固-流界面——**路径至此进入耦合核心**。

**MC 算法步骤**（对应 Bati Algorithm 2: Radiative sub-path）：

```
Loop:
  [RT 查询] 从当前位置沿当前方向 trace_ray → 命中 or Miss
  if Miss → 返回环境辐射温度 θ_R,ambient（路径终止）
  if Hit → 到达固体表面 x：
    以概率 ε：被吸收 → **进入界面耦合模块 BND**
    以概率 1-ε：反射 → 按 pr(ω|ωi) 采样新方向，继续 Loop
EndLoop
```

**FSM 状态（2 个状态，1 个 RT 挂起点）**：

- 每次弹射仅需 1 条 RT 查询，是全部模块中结构最简单的：挂起状态（RT 查询等待）+ 恢复状态（命中处理与概率分叉）。
- 恢复后根据命中信息和 Russian Roulette 结果决定继续弹射（循环）或进入 BND 模块（耦合出口）。

**模块出口与耦合接口**：命中 Dirichlet 边界（温度已知）→ 直接终止；命中温度待求表面被吸收 → 进入界面耦合模块（BND）。后者是耦合热输运区别于纯辐射渲染的关键分叉点。

#### (3) 固体传导模块（CND）——扩散方程驱动的球面随机游走（约 800 字）

**物理方程**：Bati Eq. 8（固体内纯扩散 $\partial\theta_S/\partial t = \alpha\Delta\theta_S$）与 Eq. 24（Walk-on-Sphere MC 解 $\theta_S(\mathbf{x}-\delta\hat{n}) = E[\theta_S(\mathbf{x}_{\text{WOS}})]$）。

**物理含义**：路径进入固体后，不再沿直线传播，而是进行球面随机游走模拟热扩散过程。每步跳至一个球面上的随机位置，球半径由当前位置到最近几何面的距离确定。当游走到达固体边界时，路径回到界面耦合模块（BND）进入下一轮分叉。

实现中存在两种球面游走方案，适用于不同几何环境：

##### (3a) Walk-on-δ-Sphere（M4）——固定半径近似

**物理/算法来源**：Bati §4.2。替代标准 WoS，使用固定半径 δ（而非最近面距离）的球面游走。在 Bati 原文中，此方案的动机是统一所有几何查询为射线追踪操作（无需 closest_point 查询），便于利用 BVH/RT Core 加速。在本文实现中，CP 查询已实现后端化（见 3b），因此 δ-Sphere 的独特优势不再是"避免 CP 查询"，而更多体现在其固定步长带来的数值稳定性和实现简洁性上。

**MC 算法步骤**（对应 Bati §4.2 walk-on-δ-sphere 描述）：

```
Loop:
  if 温度已知 → 路径终止
  1. 采样各向同性随机方向 Ω
  2. [RT 查询×2] 沿 +Ω 和 -Ω 各追踪一条射线，得 s+, s-
  3. δ̃ = min(δ, s+, s-) → 跳至 x + δ̃·Ω
  4. [ENC 查询] 验证新位置的腔体归属
  5. if 到达边界 → **进入 BND 模块**
  6. 时间回溯：采样指数 τ，时间倒退 → if 到达初始时刻 → 路径终止
  else → 继续 Loop
EndLoop
```

**挂起点结构**：每个游走步产生 1 个 RT 类型挂起点（双向射线对，批量提交为 1 次查询） + 1 个 ENC 挂起点（新位置腔体验证）。双向射线的物理必要性：Bati §4.2 以 $\min(s^+, s^-)$ 估计最近面距离，两条射线对同一游走步构成一对确定步长操作，不可分割。

##### (3b) Walk-on-Sphere（M9）——最近面投影精确方案

**物理/算法来源**：Muller 1956 经典 WoS 算法。使用最近面投影距离（CP 查询）作为球半径，在远离边界时收敛性更优。

**MC 算法步骤**（对应 DFS `conductive_path_wos()` in `sdis_heat_path_conductive_wos_Xd.h`）：

```
Loop:
  if 温度已知 → 路径终止
  1. [CP 查询] closest_point → 得最近面距离 d_wos
  2. if d_wos ≤ ε_shell(δ) → snap 到边界 → **进入 BND 模块**
  3. else → 均匀球面采样方向，跳至 x + d_wos·dir
  4. [CP 查询] 验证新位置的最近面距离（扩散位置合法性）
  5. if 合法性验证失败 → [RT 查询] 回退射线
  6. 时间回溯（同 3a）
  else → 继续 Loop
EndLoop
```

**挂起点结构**：每个游走步产生 2 个 CP 类型挂起点（步骤 1 的步长估计 + 步骤 4 的位置验证）和最多 1 个条件性 RT 挂起点（步骤 5，仅在位置验证失败时发生）。三个挂起点的物理必要性：WoS 球半径必须等于游走点到最近面的精确距离（CP 查询不可跳过）；验证失败的回退射线（RT）是几何非凸区域中 WoS 精度保证的必要机制。

**两方案的关系与并存理由**：WoS（3b）在远离边界的体内传导步中收敛更快（对数收敛），依赖 CP 精确步长。δ-Sphere（3a）收敛稍慢但步长固定。在本文实现中，CP 查询已后端化，两方案的选择回归纯粹的数值效率考量；实现中两者并存，由场景参数决定优先策略。

##### (3c) 瞬态传导的时间回溯

**物理方程**：Bati Eq. 34-35。$\theta_S(\mathbf{x},t) = E[H_{I,\text{cond}}\,\theta_S(\mathbf{x},t_I) + (1-H_{I,\text{cond}})\,\theta_S(\mathbf{x}+\tilde\delta\vec\Omega, t-T_{b,\text{cond}})]$

- $T_{b,\text{cond}}$ 为指数分布的向后时间跳跃，特征时间 $\tau_{\text{cond}} = \rho c\tilde\delta^2 / 6k$。
- 若时间倒退至初始时刻 $t_I$ → 使用已知初始温度终止路径。
- 若未到达初始时刻 → 继续球面游走。
- 此逻辑嵌入 (3a) 和 (3b) 的每步循环尾部，不产生额外挂起点，不需独立 FSM 状态，作为步进函数内的确定性计算执行。

#### (4) 流体对流模块（CNV）——流体边界采样驱动的温度获取（约 500 字）

**物理方程**：Bati Eq. 11（Newton 冷却定律 $\varphi_{\text{conv}} = h(\theta_S - \theta_F)$）+ Eq. 27-28（稳态流体温度 $\theta_F = E[\theta_S(\mathbf{X}_S)]$，其中 $\mathbf{X}_S \sim h(\mathbf{x})/\int_S h\,dx$）。

**物理含义**：当界面耦合选择对流模式时，需获取该流体单元（封闭腔体）的体温度 $\theta_F$。Bati 简化模型假设完美混合流体（腔体内等温），$\theta_F$ 等于腔体边界固体表面温度的 $h$-加权平均。MC 算法将其转化为：在腔体边界上按 $h(\mathbf{x})$ 成比例采样一个位置 $\mathbf{X}_S$，读取该处固体温度。若该温度未知，路径回到 BND 模块继续分叉。

**瞬态对流**（Bati Eq. 29-31）：$\theta_F(t) = E[H_{I,\text{conv}}\,\theta_F(t_I) + (1-H_{I,\text{conv}})\,\theta_S(\mathbf{X}_S, t-T_{b,\text{conv}})]$。指数采样向后时间跳跃 $T_{b,\text{conv}}$（特征时间 $\tau_{\text{conv}} = \rho c V / hS$），到达初始时刻则终止。

**MC 算法步骤**（对应 Bati Algorithm 1: Convective sub-path）：

```
1. 确定当前腔体 → 读取流体物理参数 (ρc, V, S, h)
2. [RT 查询] 初始化射线：确认路径所在腔体的几何边界
3. 采样时间跳跃 τ → if 到达初始时刻 → 返回 θ_F(t_I)
4. 在腔体边界按 h(x) 成比例采样位置 X_S → 返回 θ_S(X_S)
   → if θ_S(X_S) 未知 → **进入 BND 模块**
```

**挂起点结构**：1 个 RT 类型挂起点，位于步骤 2 的腔体边界初始化射线。此查询的物理必要性在于：腔体几何边界需要通过射线探测确认，无法从场景数据结构直接解析；腔体边界采样（步骤 4）是确定性采样，不产生挂起点。

#### (5) 界面耦合模块（BND）——能量通量连续性驱动的多模态分叉（约 1500 字）

> **本模块是 FSM 中最复杂的部分**，因此放在 RAD、CND、CNV 三个传输过程模块之后介绍：读者已熟悉 BND 所有出口目标模块的 FSM 结构，能更好地理解 BND 如何作为三种传输模式的汇聚枢纽在界面处产生多模态分叉与状态回环。物理上，界面是三种热传递模式交汇的核心节点；算法上，界面处的分叉产生不同的子路径类型；工程上，实际实现远超 Bati "didactic model" 的简化假设，须处理多种几何拓扑（固-流 / 固-固 / 外部边界）、非线性耦合（null-collision / Picard 迭代）及递归子路径。

**物理总纲**：Bati Eq. 13 / Eq. 5——在任何固-流界面处，能量守恒要求固体侧传导通量等于流体侧对流通量与辐射通量之和：

$$\varphi_{\text{cond}}[\theta] = \varphi_{\text{conv}}[\theta] + \varphi_{\text{rad}}[L_\lambda]$$

这构成了耦合的物理根源：固体温度 $\theta_S$ 不能仅由传导求出（因受辐射和对流影响），辐射场 $L_\lambda$ 也不能仅由辐射传输求出（因发射率 $\varepsilon$ 依赖于 $\theta_S$）。Bati 通过线性化和有限差分将 Eq. 13 改写为概率期望形式（Eq. 22-23），从而将界面耦合转化为蒙特卡洛路径分叉：

$$\theta_S(\mathbf{x}) = P_{\text{cond}}\,\theta_S(\mathbf{x}-\delta\hat{n}) + P_{\text{conv}}\,\theta_F + P_{\text{rad}}\int_{2\pi}\theta_R\frac{\boldsymbol{\omega}\cdot\hat{n}}{\pi}d\boldsymbol{\omega}$$

其中三个概率由物理参数决定：$P_{\text{conv}} = h/(k/\delta+h+h_R)$, $P_{\text{rad}} = h_R/(k/\delta+h+h_R)$, $P_{\text{cond}} = 1 - P_{\text{conv}} - P_{\text{rad}}$。

**界面分叉的分类（与 FSM 子模块的对应）**：

实际场景中界面有多种几何拓扑，每种对应不同的物理方程和 FSM 子模块：

| 界面类型 | 物理方程 | 分叉模式 | FSM 子模块 |
|---------|---------|---------|-----------|
| 固-流界面（温度已知）| Dirichlet BC | 直接终止 | 无（在 `BND_DISPATCH` 中判断后置 `PATH_DONE`） |
| 固-流界面（温度未知，Picard-1） | Bati Eq. 23 + null-collision | 三模态 (CND/CNV/RAD) + 辐射 null-collision 循环 | §3.3.1(5b) |
| 固-流界面（温度未知，PicardN） | 高阶 Picard 迭代 | 递归子路径树 | §3.3.1(5b) |
| 固-固界面 | Bati Eq. 26 | 二元传导注入 | §3.3.1(5c) |
| 外部环境边界 | 净辐射通量 |直射+漫射+遮挡子流程 | §3.3.1(5b) |

下文按界面事件在耦合路径中出现的先后顺序和复杂度递增展开：先介绍路径从流体侧首次到达界面的 F→S 入口过程（对应图~\ref{fig:coupled_path} 中 BND1/BND3），然后介绍固-流界面处的三模态耦合行为（BND2/BND4），最后介绍固-固界面（BND5）。

##### (5a) F→S 入口过程——界面分发与腔体归属查询（对应 BND1/BND3）

**界面入口**：当 RAD 模块中路径被固体表面吸收（以概率 $\varepsilon$），或 CND/CNV 模块中路径游走到达固体边界时，路径进入 BND 模块。虽然此过渡在代码中可能不具有显式的 `PATH_BND` 标识（RAD 吸收后直接跳转到界面处理逻辑），但它在物理上构成边界事件——路径从一个传输域（流体中的辐射传播）跨越到另一个域（固体侧的耦合处理）。

FSM 首先经过一个 **界面分发状态**（`PATH_BND_DISPATCH`），根据界面类型和温度可知性进行分流。DFS 对应：`boundary_path()` in `sdis_heat_path_boundary_Xd.h`。

**腔体归属查询——界面参数查找的前置步骤**：

- **为什么需要**：固-流或固-固界面的物理参数（$\varepsilon$, $k$, $h$）绑定于封闭腔体（enclosure）。在多腔体场景中，同一三角面片可能属于不同腔体的边界。路径到达界面后，必须先确定所属腔体才能查找正确的物理参数。
- **这一需求超出 Bati 简化模型**：Bati 假设场景由"opaque solids + transparent fluids"组成且腔体结构简单。实际工程场景（如多层建筑、多孔介质）存在大量嵌套腔体，归属判定是非平凡的几何问题。
- **算法**：6-ray 轴对齐投票方案（ENC 查询）：沿 ±x, ±y, ±z 六方向发射射线，根据命中面片的腔体标注投票确定归属；投票不一致时用随机方向回退射线补充。
- **挂起点结构**：共 3 个 ENC 类型挂起点——BVH 定位、6-ray 投票主查询、投票歧义回退查询。ENC 查询已后端化，其挂起/恢复协议与 RT 完全同构，Wavefront 主循环对所有类型统一调度（第四章详述后端侧实现）。腔体归属结果写入 `path_state`，后续全部 BND 子模块依赖此值读取正确物理参数。

##### (5b) SF 界面三模态耦合与外部环境——固-流界面处的行为（对应 BND2/BND4）

当路径从固体侧到达固-流界面（CND 游走抵达边界，即图中 BND2 类事件），或到达外部环境边界（BND4），BND 模块在此处执行耦合热输运的核心分叉逻辑。

**三模态耦合分叉**（Bati Eq. 22-23）：界面温度 $\theta_S(\mathbf{x})$ 表示为传导、对流、辐射三模态的概率加权期望——路径在此处按 $P_{\text{cond}} / P_{\text{conv}} / P_{\text{rad}}$ 概率随机选择进入 **CND 模块**（§3.3.1(3)）、**CNV 模块**（§3.3.1(4)）或发起辐射子路径（回到 **RAD 模块**（§3.3.1(2)））。这是耦合路径在界面处的基本行为模式。

**Null-collision 与 PicardN 分支——同构略述**：

> Null-collision（Picard-1 辐射接受/拒绝循环，Bati §6.3）和 PicardN（高阶 Picard 递归子路径树，Bati §6.3.3）是固-流界面耦合的两种非线性处理策略。物理层面，两者分别解决辐射概率估计不精确和高温差场景的迭代收敛问题；算法层面，两者分别引入 while 循环回边和嵌套 `sample_coupled_path()` 递归。然而，它们的 **FSM 化方法与前述模块完全同构**：
>
> - **Null-collision**：DFS while 循环 → FSM 状态回边（PENDING → 辐射子路径 → true/null 判定 → 回到界面分叉状态），与 RAD 模块的弹射循环同构——仅循环体内容不同（辐射接受判定 vs 反射/吸收概率），挂起/恢复协议完全一致。
> - **PicardN**：DFS 嵌套递归 → `path_state` 中预分配固定深度显式递归栈（最大 3 层），用栈指针模拟展开/回退。子路径复用主 FSM 全部状态集和挂起/恢复机制，不引入新的设计维度——仅增加栈管理字段。
>
> 两者的 FSM 状态已完整纳入 `path_phase` 枚举的 59 个值中（表 `tab:phase-groups`），其挂起点也已计入 §3.2 的 19 个调用点汇总。由于 FSM 化手法（识别挂起点 → 分配 PENDING/RESUME 对 → 持久化必要字段）与 RAD、CND、CNV 等模块无二致，此处不再逐一展开，以避免重复论述。§3.4.2 的端到端一致性验证将隐式覆盖这两种分支的正确性。

**外部环境净辐射通量——边界辐射源子流程（M7）**：

当路径到达场景外部边界（与外部辐射环境相交而非封闭腔体内表面）时，需计算该表面从外部环境接收的净辐射通量（太阳直射 + 天空漫射 - 自发射），对应 Bati Eq. 7 中 $\varphi_{\text{rad}}$ 的求值。MC 子流程：

```
1. [RT 查询] 直射阴影射线 → 太阳方向遮挡测试
2. [RT 查询] 漫射弹射方向 → 天空半球采样
3. [RT 查询] 漫射遮挡射线 → 确认漫射射线是否未被遮挡
4. 汇总直射 + 漫射贡献 → 计算净辐射通量
```

**挂起点结构**：3 个 RT 类型挂起点，对应子流程的三个独立射线查询步。三次查询均有明确的物理不可回避性：直射测试须通过遮挡射线而非解析计算判断太阳可见性；漫射积分须通过蒙特卡洛采样离散化（步骤 2+3 构成一次半球采样-验证对）。三步在逻辑上严格有序，每步依赖上一步结果，因此须分配独立挂起点而非合并为一次批量查询。

##### (5c) SS 固-固界面——双侧导热注入（对应 BND5）

**物理方程**：Bati Eq. 10 + Eq. 25-26。两个相邻固体子部件在界面处满足传导通量连续性：

$$k_1\frac{\theta_S(\mathbf{x}-\delta_1\hat{n})-\theta_S(\mathbf{x})}{\delta_1} = k_2\frac{\theta_S(\mathbf{x})-\theta_S(\mathbf{x}+\delta_2\hat{n})}{\delta_2}$$

改写为概率期望：$\theta_S(\mathbf{x}) = P_{\text{cond},1}\,\theta_S(\mathbf{x}-\delta_1\hat{n}) + P_{\text{cond},2}\,\theta_S(\mathbf{x}+\delta_2\hat{n})$

其中 $P_{\text{cond},1} = (k_1/\delta_1)/(k_1/\delta_1 + k_2/\delta_2)$。路径以此概率随机选择注入固体 1 或固体 2 的内部 $\delta$ 处，继续传导游走。

**MC 算法步骤**（对应 Bati Algorithm 4: Chaining selection, solid-solid 分支）：

```
1. 确定界面两侧固体的 k1, k2 + 各自的 δ1, δ2
2. [RT 查询] 双侧各 2 条射线（法线内侧 + 均匀偏移），共 4 条 → 确定两侧重注入候选位置
3. [ENC 查询] 验证候选位置的腔体归属
4. 按 P_cond,1 vs P_cond,2 随机选择一侧 → **进入 CND 模块**
```

**挂起点结构**：1 个 RT 类型挂起点（双侧 4 条重注入候选射线，批量提交为 1 次查询）+ ENC 查询对候选位置的腔体归属验证（1 个 ENC 挂起点）。4 条射线的物理必要性来自 Bati §4.2 delta-sphere 近似：注入位置依赖几何查询而非解析计算，两侧各需一组方向对。

#### (6) 完整 FSM 综合：模块组装与路径生命周期（约 400 字）

以上 5 个物理模块（RAD、BND 含 5 个子模块、CND 含 2 种方案、CNV、ENC）组成耦合热输运路径的完整 FSM。组装方式由物理耦合关系决定：

**路径生命周期**：

```
INIT → RAD ←→ BND
                ├→ CND (δ-sphere 或 WoS) → 游走至边界 → BND（回到耦合核心）
                ├→ CNV → 获取 θ_F → BND（若 θ_S 未知则继续分叉）
                ├→ RAD（辐射再发射，从新方向开始）
                └→ DONE（遇到已知温度 / 到达初始时刻 / 外部环境）
```

**复杂度的物理来源**：

- FSM 共 **59 个细粒度状态**，分属上述模块——其状态数量不是任意设计的结果，而是物理耦合的自然投影：3 种热传递模式 × 多种界面拓扑 × 非线性耦合迭代 × 瞬态时间维度 × 实际几何复杂度，每个组合需要独立的查询-挂起-恢复通道。
- **路径最短可仅 2 步**（RAD 直达已知温度表面 → DONE），**最长可达数千步**（深 PicardN 递归 + 长传导游走 + 多次界面往返）。路径长度是场景物理参数（导热率、发射率、腔体尺度）的函数，而非程序复杂度的产物。

**状态转移图总览**：所有模块的状态节点按物理过程分组着色，转移边标注触发条件（物理分叉概率 / 几何查询结果）与查询类型（RT ●/ENC ■/CP ▲），展现 FSM 的完整拓扑。

#### (7) 挂起/恢复机制（精简保留，约 200 字）

> 旧大纲 (4) 的内容精简保留。有了前述各模块对每个挂起点的物理动机解释，此处仅需概述通用的挂起/恢复协议。

### §3.3.2 Wavefront 主循环执行模型（利用前提 A，满足前提 B：可聚合性）

**篇幅**：约 1500 字  
**写作思路**：

**前承**：§3.3.1 建立了显式路径状态机，使任意多条路径可同时处于 PENDING 状态。本节以此为基础，设计 Wavefront 主循环（满足前提 B）：`collect` 阶段**消费 §3.3.1 的状态枚举与路径字段**，提取待提交查询；`distribute` 阶段**将结果写回 §3.3.1 的路径状态结构体**，恢复路径执行。

#### (1) 主循环结构

Wavefront 求解器以固定大小**路径池（Path Pool）**为核心数据结构，主循环重复"推进 → 批查询 → 恢复"的三阶段迭代直至所有像素采样完毕：

```
while（任务队列非空 or 路径池非空）:
  refill:     从任务队列填充空闲路径槽（新路径初始化）
  advance:    CPU 扫描路径池，将每条路径推进至 PENDING 状态
  collect:    从路径池收集所有 PENDING 路径的查询请求到连续缓冲区（按类型分桶）
  gpu_launch: 批量提交到 GPU（OptiX 管线）执行
  distribute: GPU 结果写回路径池对应 path_state 字段
  drain:      移除已完成路径，释放路径槽
```

#### (2) 路径池（Persistent Pool）

- 固定容量（如 24,576 条路径），所有路径的 `path_state` 结构体在内存中连续分配（数组）。
- **refill**：当路径池有空闲槽时，从像素任务队列中取出新采样任务，初始化 `path_state` 并写入空闲槽（含 STARTUP 查询）。
- **drain**：每轮循环结束后执行 Stream Compaction——扫描路径池，将已达终止状态（吸收/俄罗斯轮盘赌截断）的路径统计并覆盖，释放槽位给 refill 阶段。
- 路径池稳态运行时，填充率接近 100%，保证每批次 GPU 查询规模最大化。

#### (3) 批量射线查询与 Batch Size 权衡

- **collect 阶段**：扫描全部 PENDING 路径，将各类型查询请求写入对应类型的连续缓冲区（按类型分桶，详见本节 §3.3.2(4)）。
- **一次 GPU launch** 处理批次内所有查询请求，避免 GPU kernel 启动的 driver-level 开销摊薄。
- **Batch size 的权衡**：
  - Batch size 越大 → GPU 芯片利用率越高（RT Core 吞吐量接近峰值），CPU 每批次用于 advance/collect 的时间相对 GPU 执行时间越短；  
  - Batch size 越大 → 路径池更大 → `path_state` 数组工作集更大 → Cache Miss 越严重 → CPU advance/collect 阶段吞吐越低；  
  - Batch size 越小 → 总批次数越多 → GPU kernel 启动开销累计越高，GPU 总执行时间增加。  
  - 实测最优 pool size：24,576 条路径（在 Cache 压力与 GPU 利用率之间取得平衡）。

#### (4) 射线请求分桶（`collect` 阶段的批次组织）

- 5 种射线类型，对应不同的几何查询语义与预/后处理逻辑（辐射弹射、传导步长估计、腔体归属、阴影测试、路径初始化）。同类射线连续排列提高同批次后处理逻辑的指令一致性，降低数据局部性损耗。
- 在本实现（CPU Wavefront）中，分桶主要改善**指令一致性**而非 Warp 一致性（调度在 CPU，无 Warp 概念）。

#### (5) 等价性保证

- 状态转移逻辑（`sdis_wf_step_*`）精确对应原 DFS 函数体，仅控制结构（同步 → 异步挂起/恢复）发生变化。
- 随机数序列：DFS 与 Wavefront 生成 RNG 消耗顺序不同，但各路径的 RNG 独立，估计量期望值不变 → 统计一致性（详见 §3.4.2）。
- 确定性验证：固定路径池大小和 RNG 种子后，相同输入产生相同输出（回归测试）。

#### (6) 小结（→ 批量接口边界成立，使能 §3.3.3）

- Wavefront 主循环在 `collect` 和 `distribute` 两阶段之间，形成了明确的**批量请求 / 批量响应接口**：提交何种格式的查询请求、返回何种格式的结果，对状态推进逻辑完全透明。
- 这条接口边界将求解器职责一分为二：**状态推进**（逻辑密集、串行、Cache 敏感）与**批量查询执行**（高并发吞吐密集）。
- 两类计算资源需求迥异，接口边界天然推导出**可以、且应当**将两角色分配给不同计算单元——这是 §3.3.3 的出发点。

- 路径池生命周期状态图（路径从初始化 → 活跃推进 → 挂起等待 → 恢复继续 → 完成释放的全生命周期）

### §3.3.3 异构执行架构设计（利用批量接口，实现两角色并发调度）

**篇幅**：约 1500 字  
**写作思路**：

**前承**：§3.3.2 的 Wavefront 主循环在 `collect`/`distribute` 处形成了明确的批量接口边界，将求解器职责一分为二：**角色 A（状态推进）** 逻辑密集、串行、Cache 敏感；**角色 B（批量查询执行）** 要求高并发吞吐。两类计算资源需求迥异，接口边界天然支撑两角色分配到不同设备——本节设计这一异构调度架构。

> **核心定位声明（写作前必须明确）**：本节的贡献是 Wavefront 两角色架构下的**设备无关接口层设计**与**异步延迟隐藏调度**。GPU 在本节中以"本文选用的查询后端实例"身份出现，其选型依据（为何 GPU、为何 OptiX、为何 RT Core）完整保留给第四章独立论述。本节任何措辞不得暗示"Wavefront 要求 GPU"，只能表达"Wavefront 的两角色分离使异构后端成为可能，当后端为异步外部设备时需要延迟隐藏机制"。

#### (1) 两角色分离与异构接口层设计

**从 Wavefront 架构推导两角色**：

- §3.3.1（状态机抽象）和 §3.3.2（执行模型）的 Wavefront 主循环在结构上将求解器分为两个**功能独立**的角色：
  - **角色 A：状态推进执行者（State Advancement Executor）**——运行 `advance/collect/distribute/refill/drain/cascade`，逻辑密集，需要频繁访问 `path_state` 数组（Cache 敏感），串行或低并行度即可满足需求；
  - **角色 B：批量查询执行者（Batch Query Executor）**——接受批量查询请求（RT/ENC/CP 三类），返回查询结果，要求**高吞吐并发**（因每批次包含数万条查询），与角色 A 的数据依赖仅通过两个缓冲区（请求缓冲、结果缓冲）发生。
- 两角色在数据依赖上的解耦是 §3.3.2 Wavefront 主循环的直接产物——`collect` 阶段产出请求缓冲，`distribute` 阶段消费结果缓冲，中间的批量查询执行对状态机逻辑透明。
- **接口层的必要性**：两角色通过一个**设备无关的查询接口**（submit batch → async wait → retrieve results）交互，具体执行设备（CPU 线程池、GPU、FPGA 等）对角色 A 透明。接口层设计在本节完成，具体后端实例化留给各后端独立设计。

**明确本文选用的实例化配置**（一句话带过，不展开）：
- 角色 A 由 CPU 承担；角色 B 由 GPU 承担（批量几何查询管线的具体设计见第四章）。
- 本节其余部分聚焦于异步后端接入时的**调度架构**，适用于任何具有异步提交语义的查询后端。

架构图分层（体现接口层作为抽象边界）：

```
[ 角色 A / CPU ]  advance → collect → distribute → refill/drain → cascade
                                ↕（查询接口层：submit / retrieve）
[ 传输层 ]        请求上行（SoA格式）         结果下行
                                ↕
[ 角色 B / 后端 ]       批量查询执行（本文：GPU，详见第四章）
```

#### (2) 异步后端的延迟隐藏：双流 Ping-Pong

**动机（设备无关地描述）**：

- 当查询后端以**异步方式**执行批次时（无论是 GPU CUDA async launch、CPU 线程池 future、还是其他异步执行语义），角色 A 在提交批次后理论上无需立即等待结果，可以继续推进其他路径。
- 在严格串行的单批次循环中，两角色无法重叠：角色 A 提交批次后必须等待结果返回才能进入下一轮 advance——此时角色 B 执行期间角色 A 完全空闲，反之亦然，总利用率约 50%。
- **双流 Ping-Pong** 将路径池拆分为两个半独立批次（Stream A、Stream B），使两角色的执行时间窗口交错重叠：

  ```
  时间轴: ──[A的advance/collect]──[A提交给后端]────────────────[A的distribute]──
               同时              ──[B的advance/collect]──[B提交给后端]──[B distribute]──
                                          同时  [后端执行A批次]──────[后端执行B批次]──
  ```

- 稳态下角色 A（CPU）和角色 B（后端）接近连续忙碌，异步通信延迟被有效隐藏。
- **注**：重叠率的上限由两角色的任务时长比决定，实测稳态重叠约 35–40%（受制于 CPU advance 阶段的 Cache Miss 耗时超过后端执行耗时）。

**当后端为 GPU 时的具体时序**（本文实现）：
- GPU 执行 Stream A 批次时，CPU 处理 Stream B 上一批次的 `distribute/advance/collect`；
- 切换：GPU 开始执行 Stream B，CPU 处理 Stream A 的 `distribute/advance/collect`；
- 稳态单批次周期约 3.4–3.95 ms，GPU-CPU 实际重叠率约 35–40%。
- PCIe 传输通过 CUDA 异步 DMA（非阻塞）实现，不占用 CPU 计算线程。

#### (3) 接口层传输优化：Pinned 内存直写（O10 优化）

本优化针对"角色 A → 传输层"的数据移交过程，独立于后端类型：

- **优化前**：`collect` 阶段将查询请求写入普通内存中间缓冲区（AoS 布局），再由额外拷贝步骤转换为 SoA 布局写入 pinned buffer，触发 DMA——存在一次额外拷贝和格式转换。
- **优化后**：`collect` 直接以 SoA 布局写入 CPU 侧映射的 pinned buffer，消除中间拷贝与 AoS→SoA 转换——零拷贝触发 DMA。
- **效果**：查询提交（含 PCIe 上行）阶段耗时 92.9 s → 27.5 s（−70%）；整体墙钟时间 262.5 s → 210.1 s（约 −20%）。

#### (4) 后端内部优化：GPU 内联过滤（L4 优化）

本优化针对 ENC 查询类型的结果合并开销，属于后端侧优化（可视为第四章优化的预告，在本节以接口效果描述）：

- ENC 查询需多方向探测射线的命中结果投票，原始实现将全部候选命中下行至 CPU 做 Top-K 过滤，PCIe 下行量大。
- 优化：将 Top-K 过滤移至后端内部（GPU Any-Hit Shader）执行，接口层下行的结果已是最终投票结果，数据量大幅减少。
- 此优化说明：接口层协议（结果格式）与后端内部实现可以联合优化，但优化决策与 Wavefront 调度架构本身正交。

- 两角色接口层架构图（强调抽象边界与设备无关接口，角色 B 标注"本文实例：GPU，见第四章"）

- **并行度敏感性**：控制 CPU 线程数（8/16/32），观察 Cache 压力对加速比的影响。
- **路径池容量敏感性**：控制 pool size（8192/16384），观察工作集大小对性能的影响。

### §3.4.2 一致性验证

**篇幅**：约 1000 字  
**写作思路**：先说明为什么不能逐像素对比，再从两个互补维度证明一致性。

#### (1) 逐像素对比不适用的原因（2–3 句即可）

DFS 与 Wavefront 的 RNG 消耗顺序不同（DFS 逐路径串行消耗；Wavefront 按批次中断恢复，消耗顺序交错），导致两者产生的路径样本序列不同。逐像素差异反映随机种子差异而非算法偏差，不能解读为误差。

### §3.4.3 性能分析

**篇幅**：约 1200 字  
**写作思路**：先呈现端到端性能数据（这是已确认的硬数据），再从数据出发分析 Cache 瓶颈和路径池容量效应，最后给出架构层面的讨论。

#### (1) 端到端性能对比

**已有数据**（用户提供，最新实测）：

porous 场景，320×320×32 SPP，不同 CPU 线程数和路径池容量：

| 方案 | Pool Size | 线程数 | 墙钟时间 (s) | 加速比 $S$ |
|------|:---------:|:------:|:------------:|:---------:|
| Baseline (DFS+Embree) | — | 32 | 106 | 1.00× |
| Baseline (DFS+Embree) | — | 16 | 155 | 1.00× |
| Baseline (DFS+Embree) | — | 8 | 215 | 1.00× |
| Ours (WF+OptiX) | 8192 | 32 | 104 | **1.02×** |
| Ours (WF+OptiX) | 8192 | 16 | 116 | **1.34×** |
| Ours (WF+OptiX) | 8192 | 8 | 157 | **1.37×** |
| Ours (WF+OptiX) | 16384 | 32 | 234 | 0.45× |

**写作要点**：
- 32 线程下加速比仅 1.02×——两种架构达到性能均势 (parity)。Baseline 已充分利用全部 CPU 核心 + Embree 高度优化的 SIMD 光追；Ours 以 GPU 批量查询替代 Embree，但 CPU 侧状态管理开销抵消了 GPU 加速增益。
- 线程数受限时加速比显著提升（8 线程：1.37×，16 线程：1.34×）——Baseline 的并行度受限于 CPU 核心数，GPU 查询吞吐不受 CPU 线程数约束。
- Pool=16384 时性能剧烈退化（0.45×），直接证明 Cache 压力是主导瓶颈。

#### (2) Cache 压力分析

**核心论点**：路径池工作集大小是 CPU 侧 Wavefront 架构的主导性能约束。

- **DFS 的 Cache 优势**：DFS 同一时刻仅维护一条路径状态（在函数调用栈中），全部命中 L1/L2 Cache，内存访问效率极高。
- **Wavefront 的 Cache 劣势**：路径池中 8192 条 `path_state` 结构体的工作集大小远超 L2 Cache 容量（i9-13900K 的 L2 总量约 32 MB，单条 `path_state` 约 3–4 KB，8192 条约 25–32 MB）。每轮 `advance/cascade/distribute` 需遍历整个路径池，产生大量 LLC 缺失。
- **Pool 16384 的佐证**：Pool size 翻倍（8192→16384）导致墙钟时间从 104 s 跃升至 234 s（2.25×退化），非线性超越池容量翻倍本身——这是工作集突破 L3 Cache 容量阈值后的典型 Cache cliff 行为。

**关键结论**：Cache 压力是将计算保留在 CPU 侧的**固有代价**——Wavefront 解耦是批量化的前提，持久化路径状态是解耦的必要条件，Cache 压力是该设计选择的内在权衡，非实现缺陷。

#### (3) 架构意义讨论

**加速比不佳是有意义的科研结论**，不是负面结果：

- **架构正确性已验证**：物理一致性 + 统计等价性在 §3.4.2 中充分证明，Wavefront 改造不引入偏差。
- **瓶颈精准定位**：端到端数据 + Pool size 对比定量证明瓶颈位于 CPU 侧状态管理的 Cache Miss，而非 GPU 查询或 PCIe 传输。
- **改进方向明确**：
  - (a) SoA 布局——按字段而非按路径组织 `path_state`，减少遍历时无效 Cache line 加载；
  - (b) 状态结构体精简——分离冷/热字段（如 PicardN 的 `path_sfn_data` 已采用此策略），减小工作集；
  - (c) 查询后端优化——第四章将从后端管线设计角度独立评估 GPU 查询吞吐量。
- **线程受限场景的实用价值**：在 8–16 线程典型工作站配置下，Ours 实现 1.3–1.4× 加速，GPU 查询吞吐补偿了 CPU 并行度不足。

- 表：上述端到端性能对比表（7 行，含加速比列）。
- 图（可选，如需直观呈现）：加速比随线程数变化的折线图，标注 Cache cliff 区间。

## §3.5 小结

**篇幅**：约 300 字  
**写作思路**：

1. **回顾本章贡献**：
   - 理论层面：提出 递归到状态机 等价变换方法，将路径状态从调用栈显式化为持久 `path_state` 结构体，解耦状态推进与几何查询执行——这是将耦合热输运求解推向批量化的根本架构改变。
   - 工程层面：实现了 CPU-GPU 混合 Wavefront 求解器（含双流 Ping-Pong、Pinned 直写等关键优化）。
   - 验证层面：物理一致性验证（13 场景，282 数据点，100% 通过 3σ）+ 统计等价性检验（15.4 万像素，零显著差异）确认改造不引入系统性偏差。

2. **总结实验结论**：
   - 物理等价已验证。32 线程下 Ours 与 Baseline 达到性能均势；8–16 线程下实现 1.3–1.4× 加速。
   - Cache Miss 是 CPU 侧保留状态管理的固有代价——Pool size 对比实验（8192→16384，2.25× 退化）定量证明了这一结论。

3. **承上启下**：
   - Wavefront 改造的核心效果是将几何查询从路径执行流程中**解耦**——每个 Wavefront 迭代周期自然积累一批 RT/ENC/CP 三类批量请求，这为几何查询后端提供了清晰的工程接口：后端只需批量处理同类请求，其接口形式由 Wavefront 的分桶结构决定。
   - 第四章独立地针对三类批量查询的语义和数据特征，设计基于 OptiX 的 GPU 硬件光追管线。选择 GPU 作为查询后端的理由将在第四章自身的引言中展开论证——这是与本章并列的独立工程贡献，而非本章的附属延伸。

## 附录：否决的叙事方案——硬件中立方案

> 本节记录一个曾认真评估、最终基于技术约束否决的叙事方案。保留此记录的目的是：（1）说明当前大纲措辞为何需要如此严格；（2）防止后续修改时无意识地向此方案回退。

### 方案描述

**"硬件中立方案"（激进方案）**：将第三章整章写成硬件不特定的 Wavefront 求解框架；以 CPU Wavefront + Embree 批量接口作为本文参考实现；GPU 仅作为"一种可能的后端"在第四章独立引入，不早于第四章出现任何 GPU 依赖。

**方案的吸引力**（为何值得评估）：

- 第四章（OptiX 后端）的独立性将最自然地成立——第三章完全不提 GPU，第四章自证 GPU 的必要性，两章无任何上下游依赖；
- ENC / CP 两类查询的算法设计可以完全归属第四章，不出现在第三章接口规约层；
- 加速比评估可做两阶段：第三章验证 CPU Wavefront 相对 DFS 的架构正确性，第四章验证 GPU 后端带来的查询吞吐提升。

### 否决原因

经代码审查，发现以下技术事实，使该方案在本论文工期内不可行：

1. **批量 + 异步接口在 Embree 版本完全不存在**  
   `star3d/`（Embree 后端）与 `oxstar-3d/`（OptiX 后端）共享 `s3d.h` 接口层，但 `s3d.h` 的批量异步提交能力**仅由 OptiX 版本实现**；Embree 版本对应接口未实现或桩化。要在 Embree 后端复现批量 + 异步语义，需从零开发线程池封装，工期不具备。

2. **ENC / CP 查询语义已下沉到 GPU 后端，而非在对称接口层实现**  
   `oxstar-3d/` 中，封闭腔体归属（ENC）的多方向投票逻辑和最近面投影（CP）算法是在 OptiX Any-Hit / Intersection Shader 中实现的，并非通过 `s3d.h` 接口的对称扩展提供。原版 `star3d/`（Embree 后端）不覆盖 ENC / CP 的完整语义，缺少对应实现。因此"CPU Wavefront + Embree 参考实现"无法支撑 ENC / CP 的端到端验证。

3. **1-宽度查询有不可接受的固有开销——批量是必要工程约束，非可选优化**  
   开发初期曾在 CPU Wavefront 主循环中散落多处 1-宽度 OptiX launch 调用（每次查询单独触发一次 GPU kernel launch），实测导致性能严重下降——driver-level launch 固有开销摊薄了 RT Core 的吞吐优势。批量积累是克服此开销的必要手段，并非可以先做、后做、或选做的优化项。这一事实说明：批量查询接口的需求是由**实测固有开销的技术约束**驱动的，而非由"GPU 有并发算力"这类理论特性驱动——这正是第三章接口规约部分可以铺垫、而第四章独立展开论证的共同基础。

4. **求解器代码存在 GPU 命名泄露**  
   `stardis-oxs3d/stardis-solver/` 中，CPU 调度器侧包含 CUDA stream 类型的成员变量和双流 Ping-Pong 的流切换逻辑，代码语义上已与 GPU 后端实例耦合。这意味着即便论文叙事写成"硬件中立"，代码实现层面也无法真正剥离成 CPU-only 形态，与"CPU 参考实现"方案存在内在矛盾。

### 否决后的当前方案

当前方案选择**正视异构依赖、严格控制叙事层级**：

- **第三章叙述层**：聚焦接口需求规约（批量 + 异步必要性来自实测开销）和设备无关的两角色调度框架（`backend.submit()` / `backend.retrieve()` 抽象）；GPU 以"本文选用的查询后端实例"身份一次性点名，后续细节完全留给第四章；
- **第四章叙述层**：以两类并列贡献展开——贡献 A（满足批量异步接口约束的 OptiX RT 管线）+ 贡献 B（ENC / CP 查询的语义设计与 GPU 管线实现，为独立自主贡献）；在第四章自身引言中独立论证 GPU + OptiX 的选型理由；
- **代码现状说明**：GPU 命名泄露以"工程妥协"定性，说明可消除路径，不影响架构独立性论证。

### 对现有大纲措辞的要求

激进方案被否决的直接后果是：当前方案必须依靠**极为精确的叙事措辞**来维持第四章的独立性，而不能依赖"GPU 从未在第三章出现"这一结构性保护。凡大纲中出现与"GPU 必然性"相关的任何表述——包括但不限于"架构需要高并发后端""批量化必须使用 GPU""异步延迟隐藏依赖 CUDA stream"——均须视为**叙事安全违规**，立即修改为设备无关表述。此要求的优先级高于任何表述流畅性考虑。
